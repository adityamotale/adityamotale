If you're on a promotional or bundled _(Google One) AI Pro plan_, you get **Gemini 4
Neon** in _Gemini Web_ and _AI Studio_, while Antigravity acts like it doesn't exist.
This feels absurd when you already have access to the model but Google just can't get
its own apps to agree on that.

So I choose not to spend my day copy-pasting prompts between tabs, and built
[Setu](https://github.com/adityamotale/setu) (Saṁskr̥ta for _bridge_, recalling the
Rāmāyaṇa's causeway across the sea) to wire them together in a single tool call for
Antigravity.

## ⁕ MCP

Getting Antigravity to talk to an external model does not require hacking the IDE as
it has native support for the **Model Context Protocol (MCP)**, which means any local
binary speaking JSON-RPC over `stdio` can register custom tools and plug straight
into the agent loop.

Using this as an entry point, I've build a small MCP server written in Rust using
`rmcp`, which exposes a single `handoff` tool to agy. So, whenever Antigravity hits a
problem that warrants heavier reasoning (planning a refactor, weighing tradeoffs,
diagnosing a tricky bug, or reviewing edge cases), it calls `handoff` with context
including `task_type`, `objective`, `context`, and an optional `constraints`
paramater.

From there, the mcp simply acts as a pure local relay. It never calls an external API
or auth handles credentials. Instead, it packages those fields into a prompt payload,
forwards it over a local bridge to the Chrome extension running in _Brave_ using
websocket over localhost, and waits for the response. Once the extension returns the
output, the mcp passes it back to Antigravity over `stdio` as a standard tool result.

As far as the agent loop is concerned, it just called a local function, which happens
to provide good intelligence 😁.

> [!NOTE]
> Every MCP tool injects its description and JSON schema into the agent's context on
> every turn.
>
> Splitting workflows into separate tools burns tokens and adds tool-selection noise.
> Funneling `plan`, `decide`, `diagnose`, and `review` through one `handoff` tool via
> `task_type` keeps the prompt footprint small while still enforcing structured
> inputs.

## ⁕ Extension

Most people try to automate web apps by exporting cookies or spinning up a headless
browser, and it almost always turns into a maintenance nightmare. As I didn't wanted
to fight Google's auth or bot checks, the other half of
[Setu](https://github.com/adityamotale/setu) is just a Chrome extension sitting
inside the regular _Brave_ session.

Running inside a normal, already-logged-in browser session avoids the two annoyin
headaches right away,

1. As I'm using Brave session, no need to manage auth seperately.
2. Avoid bot checks which are very common for headless browser session.

When a prompt comes in over the localhost WebSocket, the extension navigates to
Gemini web, pastes the prompt into the input box, hits send, and then watches the DOM
while the response streams in.

Once Gemini finishes writing, it grabs the final output and sends it back over the
socket to the mcp, while also streaming progress after the tiny interval to keep the
session alive in Antigravity.

## ⁕ Why not the browser subagent?

Antigravity already ships with the built-in `browser` subagent. So the fair question
is why bother building a separate bridge at all?

The built-in browser tool spins up an isolated, sandboxed session and drives it
through a multi-step agent loop. Every prompt turns into navigation, UI inspection,
and subagent orchestration.

Running the exact same `decide` prompt on `https://gemini.google.com` makes the gap
obvious,

<>
| Approach           | Latency | Execution                                 |
|--------------------|---------|-------------------------------------------|
| Setu MCP           | 41 sec  | 1 tool call, direct DOM injection         |
| `browser` subagent | 94 sec  | 10 browser steps + subagent orchestration |

@desc Latency and step comparison for the same `decide` prompt on Gemini Web
</>

[Setu](https://github.com/adityamotale/setu) comes in at about **~2.3× faster** (~53
seconds saved on a single run) w/o burning extra subagent turns just to click around
the web UI.

> [!TIP]
> The real win isn't just raw latency. It's keeping your Antigravity context clean,
> instead of polling a browser agent across ten UI steps.

## ⁕ What's Next

Right now [Setu](https://github.com/adityamotale/setu) only targets Gemini Web, but
the bridge itself is agnostic to what's on the other side of the tab.

Adding an adapter for _AI Studio_ would bring system-prompt controls and model
parameters along for the ride. Beyond that, parallel handoffs across multiple tabs
and attaching local files or screenshots directly into the prompt are the obvious
next steps.
